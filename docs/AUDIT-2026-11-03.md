# تقرير التدقيق — MW · My Wear

**التاريخ:** 3 نوفمبر 2026 — آخر تحديث: 5 نوفمبر 2026
**النطاق:** كامل المشروع `mw/` — أكثر من 40 مساراً، 8 نقاط API، لوحة إدارة، استوديو تصميم، قاعدة Supabase.
**الطريقة:** قراءة الكود ملفاً ملفاً + تشغيل الخادم + اختبارات HTTP فعلية + اختبار المتصفح. لم يُعتبر أي شيء يعمل لمجرد وجود مكوّن له.

## 2. المشاكل الحرجة

### C1 — التخزين المحلي قد يُفعَّل في الإنتاج (لم يُصلح بعد)
`src/lib/orders.ts` يستخدم `.data/orders.json` تلقائياً عند غياب مفاتيح Supabase. على Vercel لا يوجد قرص دائم، فتُفقد الطلبات بصمت بعد كل نشر.
**الحل (المرحلة 3):** منع التخزين المحلي في `NODE_ENV=production` إلا بموافقة صريحة `ORDERS_FILE`، وإرجاع `503` واضح بدل قبول طلب لا يمكن حفظه.

### C2 — إنشاء الطلب ليس ذرّياً (لم يُصلح بعد)
`saveOrder` يُدخل الطلب ثم العناصر في طلبين منفصلين، ويعتمد على حذف يدوي عند فشل الثاني. انقطاع الشبكة بينهما يترك طلباً بلا عناصر.
**الحل (المرحلة 3):** دالة PostgreSQL `create_order` داخل معاملة واحدة (RPC).

### C3 — الخروج لم يُبطل الجلسة فعلياً ✅ مُصلح
كانت لائحة الإبطال `Map` داخل وحدة واحدة. Next.js يحزم صفحات الـ API وصفحات الـ Server Components في حِزم منفصلة، فكان الخروج يُبطل الكوكي في مسار API بينما تقبله صفحة `/ar/admin` (أُثبت بالاختبار: 200 بعد الخروج).
**الحل:** `src/lib/session-store.ts` — إبطال مشترك عبر جدول `admin_revoked_sessions` في Supabase، مع بديل `globalThis` يجمع كل الحِزم داخل العملية الواحدة. الاختبار الآن: 307 تحويل إلى صفحة الدخول بعد الخروج.

### C4 — لا منع تكرار على مستوى القاعدة (جزئياً)
إعادة إرسال الطلب قد تُنشئ طلبين على نسختين مختلفتين من الخادم لعدم وجود قيد `unique`.
**الحل الحالي:** مفتاح `Idempotency-Key` + ذاكرة العملية (يغطي النقر المزدوج).
**الحل النهائي (المرحلة 3):** عمود `idempotency_key` بفهرس فريد + معالجة داخل دالة المعاملة.

## 4. المشاكل المتوسطة

1. معاينات السلة في `localStorage` قد تستهلك الحصة مع تصاميم كثيرة (المرحلة 6).
2. أسعار التوصيل حسب المنطقة فقط، لا حسب شركة التوصيل، والأسعار الافتراضية نائبة (✅ أضيف جدول `delivery_rates` وواجهة ضبط في المرحلة 4؛ تبقى التعريفة الحقيقية مسؤولية المالك).
3. الأسعار تُنسَّق بأرقام لاتينية حتى في العربية (مقبول، لكن غير متسق مع بقية الواجهة العربية).
4. لا فصل أدوار: مدير واحد يرى كل بيانات العملاء (مقبول الآن، موثّق).
5. لا `loading.tsx` مخصص (أُضيف `error.tsx` و`not-found.tsx` بلغتين في المرحلة 10).
6. لا اختبارات آلية (المرحلة 12).
7. محرر Fabric يُحمَّل مع صفحة الاستوديو فقط، لكن حجمه كبير ويحتاج تقسيمًا/تحميلاً مؤجلاً (المرحلة 11).
8. `clientIp` يثق بـ `X-Forwarded-For` — صحيح خلف Vercel، لكنه قابل للتزييف إن نُشر الخادم مباشرة.
9. لا سجل تدقيق لإجراءات المدير (المرحلة 3/8).
10. طلبان محليان قديمان في `.data/orders.json` غير مرحّلين إلى Supabase (بيانات تجريبية).

## 5. تحسينات صغيرة

- `makeOrderNumber` كان يستخدم `Math.random` ✅ أصبح `crypto.randomBytes`.
- `favicon.ico` يعيد 404 (يوجد `icon.svg` فقط) — غير مؤثر.
- التحقق من الهاتف يرفض الهواتف الثابتة عمداً (قرار صحيح للطلب).
- `uid()` داخل الاستوديو يستخدم `Math.random` — مقبول لمعرّفات عناصر واجهة.
- لا حاجة إلى CORS أو `OPTIONS` حالياً.
- تعليقات README كانت تشير إلى كلمة سر افتراضية قديمة ✅ حُدّثت.

## 6. توصيات معمارية

1. **المعاملة أولاً:** كل كتابة طلب عبر RPC واحد (`create_order`) مع فهرس idempotency فريد.
2. **سجل الحالات:** جدول `order_status_history` يُكتب بمُشغّل (trigger) لمنع التلاعب من التطبيق.
3. **التخزين:** نقل JSON التصاميم والصور إلى Supabase Storage مع روابط موقّعة، وإبقاء المعاينات الصغيرة في القاعدة.
4. **المنتجات والمخزون:** جداول `products` / `product_variants` مع حجز مخزون داخل المعاملة.
5. **الحدود الموزعة:** Upstash Redis (جاهز، يحتاج متغيّرين فقط).
6. **الاختبارات:** Vitest للوحدات + Playwright للمسارات الكاملة، وتشغيلها في CI.
7. **المراقبة:** Sentry أو ما يعادله للأخطاء الخادمية، وVercel Analytics للأداء.

## 9. المتبقي والمعروف

- **الهجرة 004:** مطبّقة على Supabase ومختبرة (4 نوفمبر 2026): الجدول موجود (فارغ قبل الاختبار، 69 سعراً فعلياً بعد الدمج مع الافتراضي)، حفظ سعر من الـ API نجح، ظهر في قاعدة البيانات وفي `/api/delivery-rates`، ومُشغّل `updated_at` يعمل. حُذفت صفوف الاختبار. (الهجرات 002 و003 و004 مطبّقة ومختبرة على المشروع.)
- **مطلوب من المالك قبل استقبال طلبات فعلية:** إدخال تعريفة التوصيل الحقيقية من `/ar/admin/delivery` — أسعار الإطلاق 500–1300 د.ج نائبة.
- **مطلوب من المالك قبل النشر:** تم إدخال البريد `mywear.official@gmail.com` وحسابات Instagram/TikTok/Facebook في `src/lib/site.ts` — اكتمل.
- **أصول الواجهة الجديدة الناقصة:** الصورة المرجعية للتصميم، صور المنتجات الفوتوغرافية، وصور إبداعات العملاء مع موافقتهم. رابط Facebook الرسمي مُدخل. كلها موثّقة في `docs/OWNER-CONTENT.md`.
- **الوضع الداكن:** مُنفّذ عبر `data-theme` على `<html>` ومتغيرات CSS، مع سكربت قبل الرسم يمنع الوميض، وحفظ الاختيار في `localStorage` (`mw-theme`)، واتباع `prefers-color-scheme` أول زيارة. خلفية القطع تبقى فاتحة (`--color-stage`) لضمان وضوح الرسومات الداكنة.
- **حساب العميل:** غير منفّذ. أيقونة الحساب تفتح `/track` بدلاً من نموذج تسجيل وهمي. القرار (تسجيل كامل أم ضيف) ما زال عند المالك.
- **معاينات المجتمع:** 6 بطاقات SVG موسومة «نموذج» وليست شهادات عملاء. تُستبدل بصور حقيقية عند توفرها.
- **الشعار:** مُستلم ومُدمج من `public/mw-logo.svg` (نسخة حرفية، SHA256 مطابق للأصل). ملف واحد بلون `#F2F2EE` على خلفية شفافة، لذا يُعرض داخل لوحة `#111111` للمحافظة على ألوانه وشكله بدل عكسه. الهيدر والفوتر يستخدمانه على كل المقاسات.
- **مطلوب مراجعته من المالك:** نصوص الصفحات القانونية (خصوصاً مدة الـ48 ساعة للإرجاع، وصياغة حدود المسؤولية)، ثم `SITE_URL` على النطاق الحقيقي قبل النشر.
- CSP تسمح `'unsafe-inline'`؛ إزالتها تتطلب nonce وتحويل كل الصفحات إلى عرض ديناميكي (تعارض مع الأداء/SEO) — قرار موثّق.
- حدود Upstash غير مفعّلة حتى تُضاف متغيّراتها.
- 404 تُصيَّر داخل المتصفح (قيد Next.js موثّق أعلاه)؛ لا يؤثر على حالة HTTP ولا على الفهرسة.
- H5 (رفع الصور)، H7 (المخزون)، H10 (ملفات الطباعة)، H11/H12 مؤجلة إلى مراحلها المعلنة، وليست منسيّة.
